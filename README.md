# Connected Care — Multi-Tier Architecture Demo

A working three-tier demo of **Connected Care**, the pet health & safety insight layer for
PetSafe / Invisible Fence Brand: the containment collar, smart feeder, and smart fountain a
household already owns become an early-warning system for the pets' health, safety, and the
equipment itself — explained in plain language by a Claude-powered companion agent.

Built against the Connected Care PRD v1.0 and API architecture note. The demo runs the **real
`/v1` API contracts** — the presentation layer is a preview of the product, not a throwaway mockup.

## Quick start

```bash
npm install
npm run dev        # API on :3001, web on :5173 (proxying /v1)
```

Open **http://localhost:5173**. The API seeds the reference household on first boot —
Baxter & Wrigley, two Cavalier King Charles Spaniels in Chicago, with 21 days of realistic
telemetry (heart rate, walks, meals, fountain visits, device health) generated by a seeded
PRNG, so every reset is byte-identical.

```bash
npm test           # scoring-engine unit tests + full-stack API integration tests (31 tests)
npm run seed       # re-seed the database from the CLI
```

### Live Claude agents (optional)

```bash
cp .env.example .env    # add ANTHROPIC_API_KEY
```

With a key set, `/v1/agent/query` (companion chat) and insight narration run on the Claude API.
Without one — or on any API failure — both agents degrade gracefully to **deterministic
templates grounded in the same household data**, and the UI labels the mode. The demo never
breaks on stage.

## The demo script (5 minutes)

Everything runs from the **Demo control panel** (`/demo`, or the badge in the top banner).
Each trigger writes crafted telemetry through the same pipeline as production ingestion —
insights are computed and narrated live, not scripted.

| # | Trigger | What to show |
|---|---|---|
| 1 | **Reset demo household** | Dashboard: two happy dogs, "All good" state |
| 2 | **Small water dip** (info) | Insights feed with "All tiers" filter: logged quietly, no push |
| 3 | **Feeder schedule drift** (monitor) | Equipment insight, calm tone, "no action needed" |
| 4 | **Chicago cold snap** (attention) | *The differentiator:* both dogs drop together, weather explains it, sibling check prevents two alarms — one calm insight instead |
| 5 | **Fountain filter wearing out** (attention) | Same pipeline flags equipment wear → filter order suggestion |
| 6 | **Baxter's heart rate trend** (urgent) | Sibling divergence upgrades severity; breed cardiac risk at age 9 → vet recommendation. Open Baxter's page: the sparkline shows the rise above his yellow baseline band. Open chat: "How is Baxter doing?" → grounded answer + vet guidance |
| 7 | **Boundary breach + no motion** (emergency) | Toast fires in real time (SSE), dashboard goes red, **Associate alerted** chip shows the dealer routing |

## How the insight engine decides (the core differentiator)

Every reading is checked against four references (`apps/api/src/engine/scoring.ts` — pure,
fully unit-tested):

1. **Personal baseline** — the pet's own rolling 14-day mean ± stdev per metric
   (fewer than 7 days of data → insights suppressed rather than guessed).
2. **Breed cohort** — reference ranges per species + breed + size class; unlisted breeds fall
   back to a species-generic profile at reduced confidence.
3. **Household peer** — the co-housed, same-species sibling as a natural control group:
   sibling normal + weather ruled out → severity **upgrades** (the cause is this pet);
   both deviate + weather explains → severity **downgrades** (one calm message, not two alarms).
4. **Environmental context** — local weather by zip, so a cold snap explains what it can.

Severity maps to five urgency tiers — `info · monitor · attention · urgent · emergency` —
weighted by documented breed risks (a Cavalier's heart-rate trend at age 9 scores higher than
the same numbers on a young Labrador). Emergency is reserved for safety events: boundary
breach with no motion routes to the dealer associate queue in parallel with the owner push.

## Production notes (deliberate demo simplifications)

- **SQLite instead of Postgres** — the production DDL (enums, RLS tenant isolation, monthly
  partitioning of `telemetry_events`, JSONB) is preserved in spirit; every adaptation carries
  a `PRODUCTION NOTE` comment in `apps/api/src/db/schema.sql`.
- **Synchronous scoring after ingestion** — production consumes the event stream asynchronously
  so scoring can never block a device from posting data.
- **Demo-tier agent context assembly** — the server assembles pet profile + baselines + breed
  profile + insights into the prompt; production replaces this with agent tool-calling.
- **Bearer-token stub** (any token; the frontend sends `demo-token`) — production validates a
  real JWT carrying the tenant claim.
- **SSE for the stream endpoint** — push is strictly server→client, so SSE beats WebSockets on
  simplicity here; the endpoint is unauthenticated in the demo because `EventSource` cannot set
  headers (production would use a cookie or signed URL).
- Model: `claude-sonnet-4-6` per the PRD, overridable via `CLAUDE_MODEL` in `.env`.
